oraclix

A HeroClix probability engine. This page is an orientation layer over a five-document design package — it is not the specification, and it is not evidence that anything is built.

Read this first: nothing is implemented

oraclix has no application code. The repository holds five design documents and a 2024 dice prototype with four known defects. Every component on this page is Proposed unless its chip says otherwise.

The package is also internally inconsistent on purpose: it is the record of an adversarial review loop, and the newest round refuted parts of the oldest. Where documents disagree, this page follows the newest (ADV_V04 > ADV_V03 > ADV_01_V2 > SPEC_01) and marks the superseded statement Superseded. Folding those corrections back into SPEC_01 is an open task, not a finished one.

Package state: branch main at 50af635, 2026-09-21. Status vocabulary used throughout: Current · Proposed · Deferred · Verify · Superseded.

1. What it does, and does not do

A HeroClix position plus two real dials → oraclix → the probability that one character eliminates the other, with the model that produced it stated on the result.

oraclix does not play the game, advise at the table, or decide who is winning a tournament match.

DoesComputes outcome probabilities for a knock-out-only duel between Modern-Age characters, driven by real dial data. Exactly, by enumeration, where the state space allows; by seeded simulation beyond that.
Does notAct as a play aid during a live match (ruled out, ADV_V03 A1, matching SPEC_01 §6). Model victory points as a victory condition, or the tournament clock (A3). Support more than two players (A10). Parse special-power prose automatically — authoring is manual (SPEC_01 §6).
Public handoffThe committed per-set data snapshot and search index that ship with the app, plus every reported number carrying its regime label.
Offline machineryThe ingest CLI and the optional CORS proxy. The app itself never calls HCUnits — see §7; this is forced, not chosen.

The boundary that matters most is not public-versus-private — the package describes a local app with no accounts, no authentication and no secrets. It is build time versus run time. The upstream API sends no CORS headers at all, so a browser cannot call it. The ingest CLI runs on a developer machine and commits a snapshot; the running app reads only that snapshot.

A scope decision with a consequence nobody intended. Dropping victory points and the clock looks like simplification. It is not. The build total + 100 victory-point threshold (§5.2) and the tournament clock (§5.3a) are the game's only stopping guarantees — the rules' own answer to "what if you grind and cannot finish them off". Remove both and only elimination remains, and elimination is not guaranteed. A knock-out-only engine therefore models a longer-running game than real HeroClix, not a simpler one. This is the subject of §6 and it is the largest open question in the package.

The four defects in the 2024 prototype

These matter because the plan is to compose upward from exactly these functions (ADV_V04 §3.4). Fix the fourth first — reproducibility is structural.

  1. protoCombat implements "a 2 always misses" but not "a 12 always hits". §12.3b says all targets of a critical hit become hit even if the attack would normally miss. At a defence-minus-attack gap of 13 — reachable with printed values, attack 6 against defence 19 — the function returns 0.0000 where the answer is 0.0278.
  2. createDistribution computes results.indexOf(i+1) - results.indexOf(i), which returns garbage for any outcome that never came up, because indexOf returns -1. It survives only because 200,000 samples populate every bucket.
  3. protoCombat reads the global config despite taking (dist, atk, def). An ambient global is the one thing that makes a function non-composable — precisely what the bottom-up plan depends on.
  4. rollDie uses Math.random(), which cannot be seeded, so no simulation is reproducible.

The honesty constraint that falls out of the architecture

A win probability is a property of a position plus both players' policies, not of the position alone. Under genuinely optimal play by both sides the number is policy-independent — and that is attainable here only while the state space is small. The package puts the boundary at roughly 1v1 and one-against-many exact, three-against-three and up measured. The two must never share a label.

4. Walkthrough: three attacks traced end to end

Three scenarios, each teaching a different path. All three use real printed values taken from the design package; none of the data below is invented. What is proposed is the engine behaviour, because no engine exists — so read every trace as "this is what the design says should happen", never as a recorded run.

Scenario A — the ordinary attack, exactly enumerable

Provenance: real source artifact. Attacker d400GL-001bt Green Construct, printed stat line 5 / 10 / 17 / 3, no powers (ADV_V04 §2.2). Defender 2099001 Hulk at click 1, verified live against the upstream API on 2026-08-19 (SPEC_01 §3.4). The arithmetic below is exact and was computed for this page. Two stipulations, so nothing here is mistaken for a data fact: the scenario assumes an otherwise empty board, and the package quotes only Hulk's click record — not his special powers — so a real engine would still have to check those before trusting step 5.

The defender's click, as the upstream API returns it. This is one element of the dial[] array — upstream HCUnits' shape, not an oraclix contract, because oraclix has no contract yet:

{
  "click_number": 1,
  "starting_line": "auto",
  "speed_power": "leap_climb",
  "speed_value": 8,
  "attack_power": "super_strength",
  "attack_value": 10,
  "defense_power": "invulnerability",
  "defense_value": 19,
  "damage_value": 4
}
  1. rules engine Compute the minimum roll needed. §12.2a: the difference between the target's calculated defence and the attacker's calculated attack value.

    Defence 19 − attack 10 = 9 needed on 2d6. The empty-board stipulation means no Perplex, no close-combat expert and no Combat Reflexes are modifying anything, so calculated values equal printed values.

  2. rules engine Enumerate the 36 ordered outcomes. Not the 11-outcome sum. Two rules read the faces rather than the total: §12.3b and §12.3c require the dice to actually show double six and double one, and §12.6b grants knockback on doubles 2-2 through 6-6 with a hit.

    36 equally likely ordered pairs. Reduction to a sum is legal only after critical and doubles classification.

  3. rules engine Classify every outcome. 
    hit        total >= 9            10/36 = 27.78%
critical hit    faces 6-6        1/36 =  2.78%   (already inside the 10)
critical miss   faces 1-1        1/36 =  2.78%
knockback granted  5-5 and 6-6   2/36 =  5.56%   (the only doubles that also hit)

    Note 4-4 totals 8 and therefore misses — which is exactly why the sum is not a sufficient statistic: at a needed roll of 8, 4-4 and 6-2 share a total but only one grants knockback.

  4. rules engine Resolve the critical miss against the attacker. §12.3c: all targets become missed and the attacker takes 1 unavoidable damage. §12.4d: unavoidable damage cannot be reduced or prevented. §24.1: a bystander has no dial, so any damage knocks it out.

    On 1-1 — 2.78% of attacks — the Green Construct knocks itself out. A real, printed outcome that a naive model never produces.

  5. rules engine Fold in the evade branch — or skip it. Super Senses is a d6 on 5–6 when a character would be hit. A critical hit skips evasion entirely, because the target "becomes hit".

    No branch here. Hulk's click 1 shows Invulnerability, not Super Senses, so there is no evade roll to model. An engine that unconditionally multiplies P(hit) × P(not evaded) is wrong twice over.

  6. rules engine Apply exactly one damage reducer. §12.5b: only one effect that reduces damage taken may apply to a single instance of damage, and the defender chooses which. §12.4a floors damage dealt at 0. 
    normal hit    max(0, 3 - 2) = 1 click
critical hit  max(0, 3 + 1 - 2) = 2 clicks   (§12.3b adds +1)

    The choice is trivial here — Invulnerability is the only reducer on this click — so this attack does not exercise the decision. Scenario B does.

  7. exact engine Convolve into a damage distribution. 
    P(0 clicks) = 26/36 = 72.22%     (misses, including the critical miss)
P(1 click)  =  9/36 = 25.00%
P(2 clicks) =  1/36 =  2.78%
expected    = 11/36 = 0.3056 clicks per attack
  8. exact engine Map onto the dial for the probability of a knock-out.

    Verify Not computable from the package. This needs Hulk's full dial — how many clicks remain to a knock-out click — and the design documents quote only click 1. The honest output is the damage distribution plus a statement that the dial is unavailable, not a guessed knock-out probability.

Scenario B — the attack that must stop and ask

Provenance: rules text, verified. Teaches why the rules layer cannot be a single call, and why line of fire is needed at the very first rung.

Add one Probability Control character to the board. Nothing about the dice changes; the shape of the computation changes completely.

  1. rules engine Check whether Probability Control can reach the roll at all. §27.4f, verbatim: a targeted character must be within range and line of fire, minimum range 4.

    This is the finding that reorders the whole build plan. The project's build ladder defers line of fire about twelve rungs, on the reasoning that close combat never needs it. Half of that is right — §11.1 says a close attack needs no line of fire drawn. But to answer "what is the probability this attack hits" in any position containing a Probability Control character, you must already know who has line of fire to whom. Outwit (§27.4k) and Perplex (§27.4j) carry the same requirement.

  2. rules engine Suspend after the roll is seen and return a decision request. The reroll is chosen after the result is known.

    The engine emits a request — who may act, what kind of choice, what the options are — and waits. It does not decide.

  3. caller Answer it, three different ways.

    The exact enumerator takes every option, each weighted. The sampler takes one, chosen by a policy with a seeded generator. The interface asks the person. One rules implementation, three drivers.

  4. rules engine Run the contest, not the event. §21.3b: the active player gets the first chance to reroll, then the opponent, "repeated until both players decline". §21.4 runs a second such loop for die replacement. §21.11 scopes once-per-turn limits per character, not per player — so a character may use Probability Control on its own turn and on the opponent's.

    Each exercised reroll multiplies the space by another 36. Depth is therefore a function of force composition, not a constant. The engine derives the bound from board state before enumerating, and declines to sampling above a configured ceiling rather than blocking.

  5. rules engine Then the reducer choice, which is also a decision. §12.5b hands the defender the choice of which single reducer applies.

    With two reducers available this is a real branch, and the exact engine must model the damage-minimising choice. One card found in the sweep — a One-Shot reading "reduce damage taken by 1 in addition to other effects" — explicitly overrides the one-reducer limit, so reducers must be modelled as a selection with exceptions, never as a constant.

Where the enumeration bound genuinely breaks. Two cards in a 143-unit sample grant rerolls with no limiter in their text at all — one lets a character reroll the roll an opponent just rerolled; another rerolls a friendly character's Blades/Claws/Fangs result. A third lets a character roll three dice instead of two and, after any rerolls or replacements, ignore one. These are not hypothetical: they are printed card text. Four non-d6 custom dice also exist, and §21.3a says rolls using dice that are not d6s cannot be rerolled. How deep the loop actually goes is unresolved — carried as questions E2 through E5 with stated working assumptions.

Scenario C — the attack that proves the model has no ending

Provenance: real source artifact plus verified rules text. ffgc047b Slade Wilson carries Impervious and Regeneration on the same dial (ADV_V04 §2.1). The conclusion is a graph fact, not a dice estimate.

  1. rules engine Deal damage into a reducer. §12.4a floors damage dealt at 0. Impervious reduces by 2 and adds an independent d6 that reduces damage to 0 on 5–6. 
    attacker damage 2, defender reduces 2
  normal hit    max(0, 2 - 2) = 0 damage, forever
  critical hit  max(0, 2 + 1 - 2) = 1 damage, probability 1/36
  2. rules engine Heal it back. §27.3k Regeneration: roll a d6, heal a number of clicks equal to half the result. §6.11 settles the rounding — a fractional value rounds up. §6.6b caps ordinary healing at the starting line. 
    heal ceil(d6 / 2) -> {1, 1, 2, 2, 3, 3}   mean 2.0 clicks per use
healing outpaces damage 72x against Invulnerability, ~108x against Impervious
  3. exact engine Notice that the ratio is the weak argument, and replace it.

    Maximum damage through per attack is 1 click. Minimum heal per use is 1 click. So net clicks accumulated per round is ≤ 0 always — the knock-out click is not improbable, it is unreachable in the state graph. That is detectable by plain reachability, with no dice arithmetic at all. And because Regeneration costs a POWER action, a regenerating character is not attacking — so if both sides carry Impervious and Regeneration, neither can ever reach the other's knock-out click.

  4. exact engine Report three numbers, because two no longer sum to one.

    Illustrative — the shape of the output, with the worked example's figures. Not a computed result for any real pair:

    P(A eliminates B) = 0.62 · P(B eliminates A) = 0.31 · P(neither, unbounded) = 0.07
KO-only regime. Victory points (§5.2) and clock (§5.3a) not modelled.

    For the Slade Wilson mirror the triple is P(A) = 0, P(B) = 0, P(neither) = 1. Note what that does to a naive normalisation: P(A) / (P(A) + P(B)) is NaN. That test belongs in the suite before a user interface divides by zero in front of someone.

This is not a constructed edge case. Of 297 Modern characters measured, 49% carry a damage reducer, and five carry a reducer and a healer on the same dial.

5. The mechanism: exact enumeration over 36 ordered outcomes

The distinctive claim is not simulation — anyone can simulate. It is that a single attack is a finite space that can be enumerated exactly, so the answer carries no sampling error at all. The smallest useful loop:

ordered 2d6 (36 outcomes)
   -> classify: critical hit / critical miss / doubles-knockback / hit / miss
   -> [DECISION: reroll?]  each exercised reroll multiplies by 36
   -> evade d6 (6 outcomes), skipped entirely on a critical hit
   -> [DECISION: which single reducer?]
   -> damage convolution
   -> dial index  -> P(knock-out)

With no rerolls and no Shape Change that is at most 36 × 6 × 6 = 1,296 leaves — trivially exact. Shape Change multiplies by 6. Each available Probability Control reroll multiplies by 36. Two Probability Control characters per side is roughly 1.7 million leaves: still enumerable, no longer free. So the engine computes its bound first and declines to sampling above a ceiling, rather than silently taking minutes on a phone.

Why the substrate in SPEC_01 §7.2 had to change

The specification proposes a JavaScript generator that yields at each decision and is driven by three consumers. The idea is right; the substrate cannot carry it.

Superseded A generator is single-shot and cannot be cloned, so the exact enumerator cannot resume the same suspension once per branch — reroll-yes and reroll-no from one identical post-roll state. Four independent confirmations: ECMA-262 §27.8.2 gives a generator one execution context with no duplicate operation; the standard interface exposes only next, return and throw; the "generator clone" proposal died unresolved in 2014; and structured cloning explicitly refuses functions. Not a JavaScript quirk, either — OCaml 5 effects are one-shot for the same reason, and Python refuses to deep-copy a generator.

This answers SPEC_01's own reviewer-guide item 6, which asked whether the fork was cheap. It is not expensive. It is impossible.

A survey of fourteen engines — among them XMage, Forge, boardgame.io, OpenSpiel and SabberStone — found that none composes rules stages as functions. The reason is structural: currying is arity adaptation, and f(a) is a complete function that has not been called yet, not a computation that has stopped and is waiting. The pattern every forkable engine converged on independently:

Proposed — the replacement interface. No implementation exists; this is a shape, not a published signature:

// state is PLAIN DATA: structuredClone-able, no closures, no class instances,
// PRNG state stored inside it
step(state)   // -> {tag:'chance',   outcomes:[[state', prob], ...]}
              // -> {tag:'decision', who, kind, options:[...]}
              // -> {tag:'done',     result}
apply(state, choice) -> state'

The exact enumerator recurses over outcomes accumulating probability × value; the sampler picks from the same list with a seeded generator; the interface renders options. One rules implementation, three drivers — what §7.2 promised, on a substrate that can deliver it.

Where pure composition still holds. The boundary is precise: a computation stays purely composable exactly as long as every branch condition is a function of the roll and the static setup, and it stops the moment a branch condition is a player's discretionary choice. Rolling, distributions, the comparison helpers, modifier arithmetic, damage convolution and dial indexing are all pure and should stay that way. Probability Control is over the line for three separable reasons: it is decided after seeing the roll, it spends a shared per-character resource, and it contests with the opponent in a loop.

The one implementation detail most likely to produce a plausible wrong answer

Once healing exists the state graph has cycles, and on a cyclic graph the Bellman equations do not have a unique solution. A memoised recursive win-probability solver that caches a provisional value will silently settle on a wrong fixed point and return a believable number — no crash, no warning.

The fix is one line and belongs in the specification before the code is written: initialise every state's value at 0 and iterate upward, taking the least fixed point. That sequence is monotone increasing, which is what makes a turn horizon legitimate as a lower bound rather than merely an approximation.

6. The decision that changes the output: termination

This is the question a reader should leave with, because it determines what the engine emits, not merely how it is phrased.

The real game ends when one side has no characters left, when a player banks victory points equal to build total plus 100 (§5.2), or when the clock runs out (§5.3a), with §5.4 resolving even a simultaneous double defeat by victory points and then a 2d6 roll-off. There is no draw in HeroClix. Searched across the full rulebook text, loop, infinite, stalling, slow play and repetition each occur zero times. Termination is delegated entirely to the threshold and the clock — and this project removed both.

Nor can a fix be borrowed. Backgammon provably terminates by exhibiting a potential function that increases even through hits; HeroClix with Regeneration has no monotone potential, because clicks move both ways, healing has no per-game budget, and damage can be exactly 0. Magic's rules declare a draw only for loops of mandatory actions, and a HeroClix stalemate is sustained by choices, so that clause would never fire.

The cheap step that makes the choice matter less

Computing the set of states from which a knock-out can be forced with probability 1 is a polynomial graph algorithm that runs before any dice arithmetic. It catches the Slade Wilson case in microseconds. If the start state is inside that region, the probability of never ending is 0 and all five options above agree to within rounding — so the question stops mattering for most matchups. If the start state is outside it, the honest output is "these two cannot resolve by knock-out", not a number. There is even a rules precedent: a dead position in chess is exactly this test written into a rulebook.

Bundled with the termination rule is a second question that changes recommended moves, not just the report. With three outcomes there are two different zero-sum games, and the package does not yet say which one the engine solves:

GameObjectiveConsequence
G1
reachability		A maximises the probability that A eliminates B; B minimises it.A simple stochastic game with pure memoryless optimal strategies — but B is indifferent between winning and surviving forever, so B's optimal play includes pure stalling.

They coincide only when the probability of never ending is 0, and neither is recoverable from the other. Two numbers, not one.

Good news, for what it is worth: for a finite two-player zero-sum perfect-information game with chance nodes, an optimal value exists and is attained in pure strategies. Dice cost nothing here. Both places where simultaneity could have crept in are explicitly sequential — the reroll contest is active-player-first, and the reducer choice is taken after damage is known.

7. Data anatomy: upstream record to in-app state

Three boundaries, each with a different shape on either side.

Boundary 1 — upstream API to offline ingest

Forced by two measured constraints. The upstream API sends no CORS headers at all, verified with an origin request header and an explicit preflight; a browser cannot call it. Not slow, not rate-limited: impossible. And the full database is roughly 80 MB of raw JSON — 14,667 units across 333 sets, records measured at 3.3 to 8.1 KB — so bundling everything for offline use is off the table on mobile.

Superseded The documented ingest path has died since the specification was written. The set-filter query units/?set_id=<id> worked in the August audit and still worked on 2026-09-17. On 2026-09-21 it returned an empty result set for every set. The working substitute carries the same list records but still no dials, so ingest costs one request per unit — 14,667 for the full database. Why it broke is unknown — the API is undocumented, so there is no changelog, no status page and no contract to appeal to.

Verify The package disagrees with itself about the largest single set. SPEC_01 §3.5b names War of Light at 274 units as the largest, with 208 as the second-largest; ADV_01_V2 §3.15 then reports "~208 for the largest single set". One of the two is wrong, and the figure sizes the worst-case per-set ingest, so re-count before planning against it.

Two further facts about this boundary, both discovered after the specification was written:

  • The dataset mutates. One set held 135 units on 2026-09-17 and 136 four days later. A committed snapshot is a point-in-time artifact, not a stable base.
  • robots.txt asks automation to stay out of the API path — the exact path the planned ingest targets. It is a request, not a licence or a law, and the publisher itself directs players to that site for errata lookups. But a command-line tool pulling thousands of records is what that line addresses. It moves the licensing question from "no evidence either way" to "there is an explicit request, and the planned ingest runs against it". Scoping to Modern Age — 958 characters rather than 14,667 — shrinks the footprint by roughly fifteen times.

Boundary 2 — ingest to committed snapshot

The CLI filters to characters, trims to a simulation schema, validates, and fails the run on shape drift rather than writing corrupt data. Two corrections the package records about that trim:

  • Dropping collector metadata is right, but one field must be retained: the property list carries force-construction legality — unique, prime, promotional — which rarity does not. Without it, force validation cannot work.
  • Filter on the type field, which is rich and reliable, not on rank, which was null on all 25 sampled records.

A global search index also ships with the app shell: one minimal row per unit across all sets, so a name search resolves to a set to load without a network call. At roughly 60 bytes per row that is well under 1 MB.

Boundary 3 — special-power prose to executable effect

This is the project's central difficulty, and a measurement settled its size. Standard powers are structured enumerations and execute directly. Special powers are free English prose, and a dial click may simply read "special", pointing at it.

25 characters sampled at random (seed 7) from the 4 most recent sets
  with at least one special power ..... 25/25 = 100%
  prose length ........................ mean 372 characters, max 722
  dial slots reading "special" ........ 127 / 688 filled slots = 18%
  special power entries ............... 61 (trait 33, attack 11, damage 9, defense 6, speed 2)

So prose is the baseline for every contemporary figure, not an advanced case to add later. An engine covering only standard powers is not "mostly right" on modern figures — it is missing roughly 2.4 special powers and 372 characters of rules text per character, on 100% of them.

Three properties are non-negotiable: the source text is retained verbatim beside every authored effect so an encoding can always be audited against the printed power; coverage is explicit, with every figure labelled exact, partial or unmodelled and every result carrying that label; and authoring is manual by decision.

Scope leak worth knowing about. Victory points were ruled out of scope — but they are not only a scoring rule, they are a trigger and an effect inside power text. One card reads "score 25 victory points"; another "score 10 Victory Points"; ten more distinguish being removed from the game from being scored. So even a knock-out-only engine must emit a score event on a knock-out, because several powers key off whether scoring happened. The package's recommendation is to keep victory points out of the victory condition — which was the real decision — while carrying an inert counter so the DSL has somewhere to write. That is open question A16.

8. Vocabulary: the words that do not exist

A glossary was requested because the author had not read the rules in years. The most useful part turned out to be the inverse of a glossary: terms in common use that the rulebook does not contain at all. Every zero below was verified by searching the extracted rulebook text. Distinctions the rules make that code usually collapses

  • Damage dealt is not damage taken (§12.4a versus §12.5a), separated by the reducer step. A field named just damage will be wrong half the time.
  • A modifier is not a replacement value (§6.7 versus §6.8), with different application order — replace then modify, a Golden rule (§13.1) — and only modifiers are capped by the Rule of Three (§14.2, a Silver rule, so card text may overrule it). Halving and doubling are replacements. A single list of modifiers cannot represent this.
  • Powers never stack from multiple sources (§20.7, §20.8, §21.11). A character's power set is a set, not a multiset.
  • A square is a stack, not a cell with one occupant. Only two characters in one square, and anything on undestroyed blocking terrain, are forbidden; multiple markers may share a square, and the topmost non-object marker defines the terrain. Debris, smoke and barrier are markers that set terrain, not terrain types.
  • There is no round in HeroClix — players alternate turns. The word appears twice, as "round up" and "round base". A loop variable named round will collide with rounding.

Words the project must coin, because the rulebook has none: game state, dial_size, legal action set, board coordinates, policy, probability and expected value — the only occurrences of "probability" in the rulebook are the power name Probability Control — engagement, and threat range.

Historical Terms still printed in the rulebook but retired, which a scraper will happily ingest as live: Windows, Doors, Light and Heavy Objects, Colossal Stamina, Autopilot. Also note that pushing no longer exists — zero occurrences in the current rulebook, ten in the 2018 edition — and feats do not exist; the modern equivalents are Equipment, Resources, ID Cards, One-Shots, Tarot, Mystery Cards, Locations and Special Terrain.

9. Testing and the operational lifecycle

Deliberately separate from the runtime story above, because it is a different lifecycle with different owners.

LayerGate
Attack mathTable-driven cases from the rulebook: minimum roll needed, the hit/miss boundary, critical hit and critical miss, the +1 on a critical hit, 1 unavoidable damage on a critical miss.

DistributionsEvery distribution sums to 1.0 within float tolerance.
Exact versus Monte CarloThe headline gate. Sampling over a single attack must converge to the exact answer within a confidence interval. Divergence fails the build.
DeterminismSame seed, byte-identical transcript. Blocked today by the unseedable generator in the prototype.
Degenerate matchupsThe double-Impervious mirror returns the triple, and P(A) / (P(A) + P(B)) does not reach a user interface as NaN.
Line of fireGeometry gate — live-verified as rendered, not merely green. Code inspection and passing tests do not establish correctness for geometry.

Half the build ladder cannot have golden-file tests, by construction

GNU Backgammon ships two solvers, and the split is instructive. Its no-contact database is acyclic: two nested loops in topological order, one pass, exact — and the project publishes an MD5 for every such database. Its contact database is cyclic: value iteration seeded at zero, looping until a residual norm falls below a threshold. Its manual states the consequence outright — it is not possible to give a checksum for these, because the result depends on the convergence threshold, the number of restarts and rounding errors.

This ladder crosses exactly that line. Rungs without healing are acyclic: exactly solvable, bit-reproducible, golden-file testable. The moment Regeneration or Support enters, the state graph has cycles, the solver becomes iterative, and its output is not bit-identical across machines by construction, not by bug. Test those rungs to a tolerance pinned to the convergence threshold, and write that into the specification before someone files it as a defect.

Two operational problems with no clean answer yet

  • Errata rewrites dial data, and there is no feed. Figure-level errata is frequent and changes more than card text — real examples correct the values on a specific click, add a standard power to a dial, or change a range value. This is the class of errata that silently corrupts a dial database. The canonical list is a forum thread, maintained in place with an update log whose last entry postdates the rulebook pin; it is prose, paginated, edited without diffs, and the host serves a bot challenge, so a plain HTTP client cannot read it. The rulebook puts the burden on the owning player; for a simulator that becomes an ingest problem with no source. Verify whether the upstream data is errata-corrected at all — the working assumption is that it is not.
  • Sample size is the real constraint on a phone, not per-game cost. Distinguishing a 52% win rate from 50% needs 4,904 full games; 55% from 50% needs 783; a reported rate with a ±1 point confidence interval needs 9,604. A force-comparison claim of "52% versus 50%" is five thousand simulated games.

10. Later phases: the build ladder

Kept visibly separate from everything above, because none of it is close. The project's own plan is to design top-down and build bottom-up, where top-down's job is to see the dead ends early and own the testing and visualisation, while bottom-up picks the shape of each solution. That division is sound, and this review round is evidence for it: the termination hole, the line-of-fire dependency and the generator problem would all have surfaced as rework at rungs 5, 1 and 2 respectively.

The ladder runs roughly: probability of hit → turn progression with two adjacent characters of range 0 → one strong character against several → many against many on a trivial map → back to 1v1 adding powers one at a time → then open map, then range, then ranged powers, then custom testable maps, recombining each time. Two orderings in it are wrong:

RungProblemStatus
Rung 1, line of fire deferredProbability Control requires range and line of fire, so line of fire is load-bearing at the first rung, not the twelfth. Whether to model Probability Control at rung 1 — forcing a minimal line-of-fire model early — or to defer it and label rung-1 numbers "no Probability Control" is open question A15.Reordering needed
Rung 1, "no powers"No such character exists. Across the full rosters of 13 Modern sets, 0 of 958 characters have no powers; the floor is one special power and three filled standard-power slots. The only power-free elements in the dataset are bystander tokens, and they cannot reach a map except via a generator whose own trait grants Probability Control.Needs synthetic figures

The recommendation is to build the early rungs against synthetic figures and say so deliberately in the test names, adopting the Green Construct's real printed stat line — 5 / 10 / 17 / 3, one click — as the canonical synthetic figure. That is open question A14.

Two further things the ladder will need sooner than it expects: an auto-resolve default for every optional prompt — without one, an engine with this many optional triggers is simultaneously unplayable and unsimulatable, because every Impervious roll, evade and reducer choice would block — and a duration concept, since "this game" is the most common special-power qualifier in the sampled data and a state model with no durations cannot express it.

Six rules questions with no answer in the rules

Each is carried with a working assumption so work can proceed, rather than being rounded to a guess: whether a failed break away still costs an action token (assumed yes); whether one card's "reroll the roll they rerolled" re-enters the reroll contest or resolves once (assumed once, otherwise enumeration is unbounded); whether another card's Blades reroll is once per roll or unlimited (assumed once); how the four custom dice interact with the rule that non-d6 rolls cannot be rerolled (assumed not rerollable); whether a One-Shot's "in addition to other effects" overrides the one-reducer limit (assumed it overrides, because card text beats a Silver rule); and whether the upstream dials are errata-corrected (assumed not).

Decisions deliberately left open from the specification

  • Game AI search strategy Deferred — research is complete and must not be redone. The decisive finding: TD-Gammon reached world-class play at one to two ply because dice wash out the difference between deep lines, so search depth has sharply diminishing returns while evaluation quality does not. Invest in evaluation, search shallow. Note also that star-minimax pruning is a constant factor, not a change of exponent, so it does not move the state-space wall.
  • Map representation and the line-of-fire model — the largest single technical risk, and now needed earlier than planned. The geometry data already exists upstream: 737 maps, 68 of them Modern-legal, with per-square terrain and elevation, walls as lattice segments, starting-zone flags and format legality. So this is purely a geometry decision, not a digitisation project. Budget for diagonal intersections that evaluate both flanking sides and take the least restrictive, elevation-pair blocking, walls on edges, and two different metrics for the same action — range counts outward including diagonals, while line of fire is drawn centre to centre.
  • Data licensing — three-sided and unresolved. Neither data source publishes a licence or terms; one has a robots.txt that disallows the API path; and the underlying dial and map content belongs to the publisher. No evidence of enforcement against fan tools was found, which is not permission. Parked as important but not urgent.

Why "line of fire" keeps being named the risk. It is where comparable projects have died, not where they started. A 2009 effort built a working terrain model and stopped dead at line of sight; the only two HeroClix tools built in 2026 exist solely to compute line of fire and do nothing else. And no shipped play aid has ever attempted board-state entry — every tracker routes around it. That is the context for ruling the live-match play aid out of scope.

Both were re-confirmed current on 2026-09-21, and no published errata amends any of the nine rules the engine depends on. Neither document is redistributed in this repository; the package cites them by section.

One extraction trap worth carrying forward: the rulebook's §27 appendix is the better machine-readable source for the power table, because its dice render as extractable characters where the ability card's are images. But the clause granting knockback on doubles is also images, and vanishes under text extraction — a pipeline built on extracted text would conclude that doubles do nothing. It was caught only by rendering the page as an image and reading it, as were the critical-hit thresholds. Render pages whenever a threshold or a dice condition is involved.
